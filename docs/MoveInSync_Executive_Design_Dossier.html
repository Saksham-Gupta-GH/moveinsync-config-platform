1. Context & Operational Problem Statement

MoveInSync manages complex 24/7 employee commute logistics across hundreds of enterprise clients. Core backend services—booking validation, automated routing, dispatch optimization, escort-vehicle allocation, and billing—evaluate dynamic tenant policies (such as booking cutoffs, safety windows, and cancellation thresholds) on almost every request. Calling a central configuration server over HTTP on every evaluation is prohibitive.

To resolve this, I designed and implemented a production-grade multi-module Java 17 and Spring Boot 3 platform consisting of a central configuration authority and an embeddable client SDK. The SDK maintains an in-memory atomic snapshot that serves reads in ~170 nanoseconds with zero synchronized locks, while receiving live updates over Server-Sent Events (SSE) that propagate changes across 200 connected services in under 320 ms.

2. System Architecture & Data Flow

The architecture cleanly bifurcates write and read paths. Consumer microservices (Dispatch, Routing, Billing) execute configuration reads exclusively against in-memory snapshots held in heap. Updates are authored by operations staff via REST, atomically validated, fsynced to disk within SQLite WAL transactions, and fanned out over persistent SSE streams.

3. Consistency Model & Invariants

The system provides global monotonic version progression under a single writer lock on the server, paired with monotonic snapshot isolation on client SDKs. When an administrator publishes a changeset, the server acquires a dedicated reentrant writer lock, validates all keys atomically, assigns a monotonically increasing version integer, forces a durable fsync to SQLite WAL storage, and emits the delta to connected subscribers. Client SDKs observe monotonically non-decreasing versions. Multi-key queries execute against an immutable snapshot, guaranteeing that no consumer ever sees partial compound state. Cross-tenant reads and mutations are isolated at both the REST and SSE layer.

4. Eliminating Read Contention: The Atomic Snapshot Pattern

Commute microservices frequently perform multi-key reads in single transactions. For instance, when evaluating an employee cab request, the booking service inspects both booking_cutoff_minutes and cancellation_window. Using a mutable map creates a critical race condition: a background delta push could mutate the second key while the first key is being read, causing the service to evaluate mixed-version business rules.

While traditional ReadWriteLock primitives prevent partial reads, they introduce synchronization overhead and thread starvation under peak dispatch bursts. To achieve zero-lock performance, the SDK holds an immutable ConfigSnapshot record referenced by an AtomicReference<ConfigSnapshot>. Services bind the reference once:

ConfigSnapshot snapshot = client.getSnapshot();
int cutoff = client.get(snapshot, "booking_cutoff_minutes", Integer.class);
int window = client.get(snapshot, "cancellation_window", Integer.class);

All evaluations execute against that immutable snapshot instance with zero synchronized locks, zero thread contention, and zero network calls. When an SSE delta arrives, the SDK computes a new immutable snapshot and swaps the pointer in one atomic instruction (AtomicReference.set()). In a 50-thread concurrent stress test executing 2,100,000+ continuous reads during active compound updates, zero partial state violations occurred.

5. Staged Rollouts and the False-Gap Solution

During initial testing of staged canary rollouts, targeting Bangalore offices with Version 44 caused Hyderabad nodes to observe a version jump (v43 → v45). Their local gap detectors assumed network packet loss and triggered an aggressive storm of REST catch-up queries to the server.

I solved this by introducing contiguous monotonic empty deltas: when a canary changeset commits (Version 44), the server broadcasts the full payload to Bangalore subscribers, but transmits an empty delta (empty=true) to Hyderabad subscribers. This advances Hyderabad's local version counter to 44 without altering its values, completely eliminating false gap alarms while maintaining total version alignment across the fleet. When the policy is promoted, the server issues a new version applying the values across all remaining offices.

6. Sequence Diagram: Packet Drop, Gap Healing & Stale Duplicates

Delayed duplicate handling: If delayed re-transmissions deliver an older packet (e.g. Version 41 arriving after Version 43 is active), the client's monotonic check (if (delta.version <= currentVersion) return;) immediately discards it as a safe idempotent no-op, preventing stale state from corrupting newer configurations.

9. Architectural Trade-Offs & Deliberate Omissions

1. Omitted Distributed Consensus (Raft / Paxos): For MoveInSync's operational profile (infrequent administrative writes, millions of in-memory reads), embedding SQLite WAL with full fsync durability provides single-node simplicity with zero distributed consensus failure modes. Estimated write capacity is ~2,500 writes/sec (unbenchmarked under multi-node distributed load). For multi-region clustering, migrating to PostgreSQL with read replicas is preferred over Raft.

2. Omitted Complex CRDTs: Tenant transport configurations follow top-down administrative authority (Shift > Office > Client > Global). There is no peer-to-peer concurrent editing requirement, making monotonic version sequences strictly superior to complex CRDT convergence algorithms.

3. SSE vs. WebSockets: Chose SSE over WebSockets because configuration propagation is strictly unidirectional (server-to-client), operates cleanly over standard HTTP/1.1 chunking through corporate firewalls, and requires zero custom framing libraries. Estimated single-node capacity is 10,000–15,000 concurrent SSE connections.
